# frontendv1 主站分层与角色导向设计

日期：2026-06-10

主题：基于后端真实能力重构 `frontendv1` 的主站体系，形成游客、学生、管理员三类主站，并以就业方向闭环作为首个深挖样板。

## 1. 背景

当前仓库中的既有前端已经覆盖了社区、题库、考研、考公、就业、留学和管理员后台等大量页面，但整体入口仍然偏“模块平铺”：

- 登录前后容易回到同一个全站首页语境
- 多个方向功能更像并列陈列，而不是“按身份进入，再按任务深入”
- 页面层级感不够强，部分页面更像把多个功能摊在一个屏幕里
- 游客、学生、管理员虽然功能不同，但主站体验差异还不够明确

用户本轮明确要求：

- 设计新的 `frontendv1`
- 必须依据后端真实能力设计，不能虚构功能
- 功能使用时要逐层深入，不能把很多功能直接摊开在一个页面里
- 每一层都要有清晰、明显的返回路径
- 提示语、状态反馈、边界说明必须明显，不能藏成灰色小字
- 风格要商业化、产品化，而不是朴素大块面板或 AI 模板感布局
- 游客、学生、管理员主站都要分别设计
- 学生进入后，除公共能力外，其余主站效果要随方向不同而变化
- 主体品牌风格保持一致，但因角色与方向不同而调整布局、密度与优先级

## 2. 后端现实约束

`frontendv1` 的主站设计必须服从后端现有能力，而不是按理想化平台结构画完全对称的页面。

### 2.1 用户方向由后端决定

后端 `User` 实体已存在 `target` 字段：

- `kaoyan`
- `kaogong`
- `job`
- `liuxue`

这意味着学生登录后的主站不应由前端自行猜测，而应通过用户信息接口读取方向后进入相应方向站。

相关接口与实体：

- `backend/src/main/java/com/graduateplatform/common/entity/User.java`
- `GET /api/users/me/profile`
- `GET /api/users/me/dashboard`

### 2.2 公共能力真实存在且应保留在主站壳子外层

以下能力不属于某一个方向私有：

- 社区
- 题库
- 个人中心

因此它们不应被埋进某一个方向站的内部导航，而应作为全站公共能力，始终保留在公共层或角色壳层中。

### 2.3 各方向成熟度不对称

后端能力并非四个方向完全对称：

- 就业：学生闭环与管理员闭环都完整，适合做最深样板
- 考研：学生侧强，管理员侧也有真实数据与审核能力
- 考公：学生侧和管理员数据维护都存在，但产品闭环成熟度次于就业
- 留学：学生自助能力很完整，但没有独立的 `/api/admin/studyabroad/**`

因此前端主站不能做成四个方向完全同构的对称首页，否则会制造“前端承诺强于后端现实”的落差。

### 2.4 通知体系是分域存在，不是统一消息中台

当前后端存在多类通知或未读计数：

- 社区通知
- 就业通知
- 考公通知
- 考研咨询未读数

这意味着 `frontendv1` 不应伪造一个完整的“全平台统一消息中心”。若后续需要汇总展示，只能做前端聚合摘要，不应在设计上暗示后端已经有统一消息域。

### 2.5 留学方向的前后端命名存在映射问题

后端用户方向值使用：

- `liuxue`

现有前端路由使用：

- `/studyabroad`

`frontendv1` 必须显式定义这层映射关系，避免方向分流与路由跳转之间出现语义断层。

## 3. 目标

本次设计的核心目标不是“再做一个首页”，而是建立一套可落地的主站体系：

1. 登录前后信息架构清楚
2. 游客、学生、管理员入口语义明确不同
3. 学生主站由后端方向驱动
4. 公共能力持续可达，不因方向站出现而消失
5. 每层页面只承担当前层级的任务，不承载所有功能
6. 深页始终有明确返回路径与状态提示
7. 视觉上形成统一品牌，但不同角色有明显气质差异
8. 以就业闭环作为 `frontendv1` 首个深挖样板

## 4. 范围

### 4.1 本次设计包含

- `frontendv1` 的主站信息架构
- 三类主站定义：游客主站、学生主站、管理员主站
- 学生方向分流规则
- 公共能力在主站中的定位
- 就业方向作为第一深挖样板的页面层级
- 管理员总台与真实后台模块的映射关系
- 页面级返回路径与提示语规则
- `frontendv1` 视觉方向与品牌气质原则

### 4.2 本次设计不包含

- 具体组件代码实现
- 全站所有深页一次性重写
- 统一消息中心后端改造
- 留学独立管理员后台的虚构设计
- 新增后端接口或修改现有后端数据结构

## 5. 总体策略

本次 `frontendv1` 采用如下总体策略：

- 新建独立前端目录，而不是在现有前端上直接大改结构
- 先做“全平台壳子 + 就业闭环最深”
- 公共能力继续保留为公共入口
- 登录后按角色进入不同主站壳
- 学生主站再按 `target` 进入不同方向工作站
- 管理员不进入学生式首页，而是进入平台总台

## 6. 主站分层模型

`frontendv1` 采用四层分流模型。

### 6.1 第一层：公共入口层

面向所有访问者，包括游客。

该层的职责是：

- 提供公共内容探索入口
- 解释平台的四个方向与公共能力
- 在不登录的前提下允许浏览公开内容
- 在需要身份的动作出现时明确提示“登录后继续”

这一层不负责：

- 复杂业务编辑
- 个人工作流维护
- 平台治理

### 6.2 第二层：身份分流层

用户完成登录后，不再回到游客语境，而是按角色分流：

- 游客：仍停留在公共浏览语境
- 学生：进入学生主站壳
- 管理员：进入管理员总台壳

这一层的目标是让“谁在使用平台”成为页面结构的一部分，而不是仅存在于权限逻辑里。

### 6.3 第三层：方向决策层

仅作用于学生。

学生主站壳在获取用户资料后，根据 `target` 进入对应方向工作站：

- `kaoyan` -> 考研工作站
- `kaogong` -> 考公工作站
- `job` -> 就业工作站
- `liuxue` -> 留学工作站（前端路由映射为 `/studyabroad`）

不同方向使用同品牌、不同布局密度与优先顺序。

### 6.4 第四层：任务深挖层

当用户进入某一方向站后，不在主站上直接完成所有工作，而是按任务继续进入下一层：

- 列表页
- 详情页
- 编辑页
- 结果反馈页

每一层只承担一个明确目标，并且明确返回上一层。

## 7. 三类主站定义

### 7.1 游客主站

游客主站不是“空壳页”，而是公共浏览站。

#### 7.1.1 目标

- 让用户先理解平台价值
- 让用户先逛公开内容
- 让登录动作在真正需要时出现

#### 7.1.2 可见能力

游客主站应直接可达以下内容：

- 社区帖子列表与详情
- 题库目录与公开题库入口
- 就业公开招聘会与岗位详情
- 考研公开院校、分数线、公开资料与自习室列表
- 考公公开岗位、分数线、考试日历
- 留学公开院校、录取案例、经验内容

#### 7.1.3 不可在游客层执行的动作

- 发帖、评论、收藏
- 创建计划、材料、申请
- 简历编辑与投递跟踪
- 进入个人方向工作站

#### 7.1.4 页面语义

游客主站应该更像“可逛的公共站”，而不是“功能被锁住的登录页”。

它的界面应强调：

- 公开内容流
- 热门方向入口
- 公开榜单
- 明确的“登录后解锁”提示

#### 7.1.5 返回路径

- 公共详情页 -> 返回对应公共列表
- 公共列表页 -> 返回游客主站
- 登录成功后 -> 再进入角色主站，不强行回到游客页细节处

### 7.2 学生主站

学生主站是方向工作站壳，不是全功能卖场。

#### 7.2.1 目标

- 让学生先看到今天最该推进的下一步
- 保留社区、题库等公共入口
- 让方向工作流成为主导航中心

#### 7.2.2 共通区

无论哪个方向，学生主站都保留：

- 社区入口
- 题库入口
- 个人中心
- 用户方向标识
- 模块级摘要提醒

#### 7.2.3 差异区

不同方向优先展示内容不同：

- 就业：简历、推荐、投递跟踪
- 考研：计划、资料、1v1 咨询、自习室
- 考公：岗位匹配、分数线、考试日历、模拟面试
- 留学：申请项目、时间线、材料、经验库

#### 7.2.4 页面语义

学生主站不直接塞满所有页面，而是只展示：

- 当前阶段最重要的 2 到 4 个任务入口
- 当前状态摘要
- 关键提醒
- 下一步动作

#### 7.2.5 返回路径

学生方向站的深页返回逻辑统一为：

- 深任务页 -> 返回方向工作站
- 列表详情 -> 返回原列表页
- 结果反馈 -> 返回操作来源页

### 7.3 管理员主站

管理员主站应被定义为“平台总台”，而不是学生工作站换皮。

#### 7.3.1 目标

- 先处理平台秩序与风险
- 再分发到各真实后台模块
- 让管理员先判断优先级，而不是一进来就掉进某个表格

#### 7.3.2 真实后台模块映射

管理员主站只映射后端真实存在的管理能力：

- 内容治理
  - 待审核帖子
  - 举报处理
  - 评论举报处理
  - 社区分类管理
- 用户治理
  - 用户状态管理
  - 按方向与状态筛选
- 就业运营
  - 招聘会管理
  - 岗位管理
  - 站内提醒触发
  - 简历附件安全摘要
- 方向数据治理
  - 考研院校与分数线
  - 考研资料审核
  - 考公岗位、分数线、考试日历
- 题库治理
  - 题库管理
  - 题目管理
  - 批量与快照

#### 7.3.3 留学边界

管理员主站不得伪造“留学独立运营台”。

留学相关治理只能通过以下通用模块间接处理：

- 社区内容治理
- 用户治理

#### 7.3.4 页面语义

管理员主站应该像“平台总台”：

- 高优先队列先展示
- 风险、审核、治理优先
- 进入具体后台模块后再做列表与编辑

而不是：

- 学生式欢迎页
- 多个后台表格直接堆满首页

#### 7.3.5 返回路径

管理员侧统一返回链路：

- 总台 -> 某运营台
- 运营台 -> 列表页
- 列表页 -> 编辑页 / 详情页
- 结果反馈 -> 返回列表页
- 列表页 -> 返回运营台
- 运营台 -> 返回总台

## 8. 就业方向作为首个深挖样板

就业模块是 `frontendv1` 首个深挖方向，因为它拥有最完整的学生闭环和管理员闭环。

### 8.1 学生就业闭环

后端支持：

- `GET/PUT /api/job/preferences`
- `GET/PUT /api/job/resume`
- `POST /api/job/resume/file`
- `GET /api/job/resume/file/download`
- `DELETE /api/job/resume/file`
- `GET /api/job/recommendations`
- `GET/POST/PUT/DELETE /api/job/applications/**`
- `GET/PUT /api/job/notifications/**`

#### 8.1.1 就业工作站

主站只展示三条主路径：

- 完善简历
- 查看推荐
- 管理投递

以及三个摘要：

- 简历完成度
- 今日推荐数
- 待跟进投递数

#### 8.1.2 简历页

简历页负责：

- 在线简历字段维护
- 简历附件上传、替换、下载、删除

必须出现明显提示：

- 附件只保存与下载
- 附件不参与自动解析

#### 8.1.3 推荐页

推荐页负责：

- 条件筛选
- 匹配结果浏览
- 匹配原因展示
- 进入岗位详情

不负责：

- 在线简历编辑
- 投递列表维护

#### 8.1.4 岗位详情页

岗位详情页只做两件事：

- 加入投递跟踪
- 打开外部申请链接

必须出现明显提示：

- 平台内不会自动投递
- 外部申请将跳转站外

#### 8.1.5 投递跟踪页

投递跟踪页负责：

- 新增、编辑、删除投递记录
- 维护投递状态
- 维护下一步事项
- 展示当前简历附件状态

### 8.2 管理员就业闭环

后端支持：

- `GET/POST/PUT/DELETE /api/admin/employment/fairs/**`
- `GET/POST/PUT/DELETE /api/admin/employment/jobs/**`
- `POST /api/admin/employment/notifications/trigger`
- `GET /api/admin/employment/resumes`

#### 8.2.1 总台入口

管理员总台首页只显示：

- 招聘会数量与活跃状态
- 岗位数量与活跃状态
- 待触发提醒任务
- 已上传简历摘要数量

#### 8.2.2 就业运营台

进入就业运营台后，再分为：

- 招聘会列表页
- 岗位列表页
- 提醒触发页
- 简历摘要页

不得在总台首页直接展开四类完整管理对象。

## 9. 方向主站差异化规则

### 9.1 共通品牌

三类主站必须共用同一品牌语言：

- 同一基础色系
- 同一排版系统
- 同一基础组件逻辑
- 同一提示语风格

### 9.2 角色差异

在统一品牌下拉开以下差异：

- 游客站：更强调内容探索、公共可达、开放感
- 学生站：更强调个人任务、下一步推进、节奏感
- 管理员站：更强调治理优先级、风险、队列与运营分发

### 9.3 信息密度差异

- 游客站：内容导向，留白相对更多
- 学生站：任务导向，中等密度
- 管理员站：治理导向，密度最高，但必须有清晰分栏和层级

## 10. 提示语与反馈规则

本次设计中，提示语不是装饰性文案，而是流程结构的一部分。

### 10.1 必须明显呈现的提示类型

- 登录后继续
- 站外跳转
- 只读摘要
- 不支持当前操作
- 当前操作的下一步
- 操作完成后的返回位置

### 10.2 典型必须强调的边界说明

- 简历附件不参与自动解析
- 平台内不会自动投递
- 管理员只能看简历附件安全摘要，不能下载或替换
- 留学没有独立管理员后台
- 当前页面处于公共浏览层

### 10.3 反馈原则

所有关键动作都应有明确结果反馈：

- 成功
- 失败
- 权限不足
- 数据为空
- 下一步建议

## 11. 返回路径规则

`frontendv1` 必须把返回路径设计为显式结构，而不是依赖浏览器后退。

### 11.1 主站级返回

- 公共深页 -> 返回游客主站
- 学生深页 -> 返回对应方向工作站
- 管理员深页 -> 返回对应运营台或总台

### 11.2 列表级返回

- 详情页 -> 返回原列表
- 编辑页 -> 返回来源列表
- 结果反馈 -> 返回操作来源页

### 11.3 禁止情况

禁止出现以下情况：

- 用户完成操作后，不清楚应回哪一层
- 学生从方向深页返回到游客语境
- 管理员从运营深页返回到学生式首页

## 12. 路由与实现边界建议

### 12.1 前端目录策略

按照用户已确认的方向，`frontendv1` 应作为独立目录存在，不直接覆盖当前 `frontend`。

### 12.2 路由壳层建议

建议至少定义三类壳层：

- 公共壳
- 学生壳
- 管理员壳

学生壳内部再做 `target` 分流。

### 12.3 留学映射规则

前端路由仍使用 `/studyabroad`，但用户方向判断必须接受：

- `liuxue` -> `/studyabroad`

## 13. 非目标

本设计明确不追求：

- 一次性重做所有深页
- 四个方向完全同构
- 在前端层制造统一消息中台假象
- 让游客拥有需要认证的复杂功能
- 让管理员首页承担所有操作细节

## 14. 成功标准

若后续实现满足以下条件，则视为本次设计成功：

- 登录前后语义明显不同
- 游客、学生、管理员主站一眼可区分
- 学生主站由后端方向驱动
- 公共能力未因方向站而丢失
- 功能路径呈现为逐层深入，而非首页平铺
- 页面中的返回路径与边界提示显著可见
- 就业方向形成第一条完整闭环
- 管理员总台只承接真实后台能力，没有伪造留学独立后台

## 15. 实施优先顺序

后续进入实现时，建议顺序如下：

1. 建立 `frontendv1` 基础壳层与角色分流
2. 建立公共壳与游客主站
3. 建立学生壳与就业工作站
4. 完成就业闭环深页：简历、推荐、岗位详情、投递跟踪
5. 建立管理员总台与就业运营台入口
6. 再扩展考研、考公、留学方向工作站
