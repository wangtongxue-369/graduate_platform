# 管理后台主题统一与层级整理设计规格

日期：2026-06-02

主题：管理后台与全局主题系统对齐

## 1. 目标

在不改动后台业务能力和主要信息架构的前提下，把管理后台从“沿用前台通用卡片样式的管理页”整理为“与全站主题一致、层级更清晰、支持全局主题切换的控制台界面”。

本次设计重点解决以下问题：

- 后台页面混用 `feature-card`、`track-card`、`admin-surface-card`、`tag tag-btn` 等不同语义样式，导致视觉气质不稳定。
- 筛选区、统计区、数据区、操作区的主次关系不够稳定，后台扫读效率偏弱。
- 部分后台控件仍然更像前台内容页组件，而不是管理控制台组件。
- 后台主题必须跟随全局主题切换，但现有后台页面的设计约束还不够明确，后续容易回退到局部硬编码样式。

## 2. 设计结论

本次采用“控制台化统一”方案。

核心结论如下：

- 延续当前全站的深色/浅色双主题、青绿色品牌高亮、柔和玻璃感表面语言。
- 后台不做另一套独立视觉系统，而是在现有主题 token 体系之上，建立一组更克制、更高信息密度的后台语义样式。
- 后台页面统一为三段层级：
  - 顶部摘要区：标题、说明、关键统计、快捷入口
  - 中部工具区：筛选、切换、搜索、批量动作
  - 底部数据区：表格、卡片列表、表单维护面板
- 全部后台页面必须接入并服从全局主题切换，不允许新增后台专属主题状态。

## 3. 范围

本次设计包含：

- `frontend/src/pages/admin/**` 下管理后台页面的视觉统一与层级整理
- `frontend/src/App.css` 中后台共享样式区的重组
- `frontend/src/index.css` 中后台需要补充的语义 token 映射
- `frontend/src/App.adminTheme.test.js` 的覆盖增强
- 后台页面对全局主题切换的显式对齐规则

本次设计不包含：

- 后台业务流程重写
- 管理接口字段调整
- 登录流程改造
- 批量操作、权限模型、导航结构的大范围重构
- 后台页面的内容文案全面重写

## 4. 设计原则

### 4.1 统一优先

后台页优先复用统一的后台语义样式，不再继续直接借用前台内容卡片样式完成管理界面。

### 4.2 层级清晰优先

每个后台页都要让用户在首屏清楚分辨：

- 这页在管理什么
- 现状是否正常
- 当前可筛选什么
- 当前可操作什么
- 数据主区域在哪里

### 4.3 主题一致优先

后台必须和前台一样，完全由全局主题系统驱动。主题切换只允许通过现有 `PreferencesContext` -> `document.documentElement.dataset.theme` -> CSS 变量映射生效。

### 4.4 克制的控制台感

后台比前台更强调稳定、秩序、扫读效率，因此会减少前台较强的展示感与漂浮感，但不会脱离当前全站品牌气质。

## 5. 当前结构问题归纳

### 5.1 容器语义不统一

后台页当前同时使用：

- `feature-card`
- `track-card`
- `admin-surface-card`
- `feature-card metrics`

这些容器在圆角、内边距、背景层次、用途语义上并不一致，导致同一页内看起来像不同模块拼接。

### 5.2 筛选控件仍偏前台感

`ReviewPage`、`UserManagementPage` 等页当前大量使用 `tag tag-btn` 作为筛选器。它更像内容标签，不够像后台控制器，选中态与 hover 态的视觉权重也不稳定。

### 5.3 数据区层级松散

统计卡、列表卡、状态标签、按钮区之间缺少稳定的“摘要 -> 筛选 -> 数据 -> 操作”节奏，导致后台虽然可用，但管理感不足。

### 5.4 主题切换约束需要前置

当前后台共享样式已经基本建立在 token 之上，但页面结构和组件选型还没有把“必须跟随全局主题切换”写成设计规则。若继续沿用零散容器和旧类名，后续很容易再引入硬编码色值或仅适配浅色主题的样式。

## 6. 目标页面骨架

所有后台页面统一采用以下骨架：

### 6.1 顶部摘要区

组成：

- `eyebrow`
- 页面标题
- 页面说明
- 关键统计或页面级反馈
- 可选的返回入口

要求：

- 标题与说明区域保持稳定留白
- 关键状态优先放在摘要区，而不是埋在数据列表里
- 错误、提示、成功信息使用后台语义消息面板，而不是临时杂糅到任意卡片里

### 6.2 工具区

组成：

- 筛选器
- 状态切换器
- 搜索框
- 批量操作或快捷操作

要求：

- 工具区统一使用后台专属容器
- 筛选器统一为分段式或工具条式样式，不再使用前台内容标签风格作为主筛选器
- 工具区与数据区视觉上需要明显分层

### 6.3 数据区

组成：

- 表格
- 记录卡片列表
- 表单维护面板

要求：

- 数据区是页面主视觉重心
- 记录项统一采用“信息在左、状态在中、动作在右”或其在移动端的垂直变体
- 表单维护类页面使用统一的左右双区或上下双区布局

## 7. 组件与样式语义设计

### 7.1 后台共享容器

统一以 `admin-surface-card` 作为后台主容器基元。

用途：

- 筛选面板
- 表单维护面板
- 数据列表面板
- 统计摘要面板

设计要求：

- 圆角、边框、背景、阴影完全由语义 token 驱动
- 浅色与深色主题下只通过 token 切换，不使用页面内分支逻辑
- 后台主容器的层级强于前台 `feature-card`，但弱于全局 modal

### 7.2 后台摘要卡

新增或整理一组后台摘要卡语义，用于首页和各管理页顶部统计。

目标特征：

- 数字层级更明确
- 标签和说明更收敛
- 不使用过强的前台展示渐变
- 在深色主题下仍然具有良好数字可读性

### 7.3 后台筛选器

筛选器统一替代当前以 `tag tag-btn` 为主的方案。

目标特征：

- 更接近 segmented control / filter bar
- 选中态通过边框、背景和文字权重表达，而不是仅靠品牌底色
- 支持多组筛选并排出现时仍保持秩序感

设计结果应适用于：

- 审核状态切换
- 用户方向筛选
- 用户状态筛选
- 数据源启用/停用切换

### 7.4 后台状态标签

继续保留 `admin-status-chip` 语义，但统一约束其使用场景：

- 表示业务状态，不承担筛选器角色
- 成功、警告、危险、中性四类语义保持一致
- 在浅色/深色主题下都维持稳定的可读性与对比度

### 7.5 后台操作区

统一 `admin-inline-actions`、`admin-row-actions` 的布局节奏。

要求：

- 主操作优先使用 `btn primary`
- 风险操作使用 `outline-danger` 或更克制的危险样式
- 普通次级操作统一使用 `outline-neutral` 或 `ghost`
- 同一行操作按钮不要再混入过强的前台标签样式

### 7.6 后台消息面板

继续使用后台语义消息容器承载：

- 错误提示
- 操作结果
- 补充说明

要求：

- 不依赖硬编码浅红或浅绿背景
- 必须映射到全局状态 token
- 深色主题下不出现“信息块亮度突兀”的问题

## 8. 页面级设计映射

### 8.1 `AdminPage`

目标：

- 让首页更像管理控制台入口，而不是普通功能卡片集合

调整方向：

- 顶部放摘要信息和全局统计
- 中部放快捷操作面板
- 下部放管理能力入口卡
- 所有入口卡在结构上统一，不混用前台内容卡片语义

### 8.2 `ReviewPage`

目标：

- 强化“审核工作流”的管理感和扫读效率

调整方向：

- 筛选器升级为后台工具条
- 帖子卡片统一为后台记录卡
- 元信息、状态、审核操作、处理原因形成稳定层级
- Markdown 预览容器与审核操作区拉开主次

### 8.3 `UserManagementPage`

目标：

- 强化筛选、统计、用户状态变更之间的控制关系

调整方向：

- 顶部保留统计摘要
- 双组筛选统一到后台工具区
- 用户记录卡统一结构
- 状态变更操作不再用前台标签交互气质承载

### 8.4 `EmploymentManagementPage`

目标：

- 让“左侧维护表单 + 右侧数据列表”看起来属于同一后台系统

调整方向：

- 双列表、双表单全部纳入统一后台容器
- 列表项的信息、状态、动作区统一
- 表单字段区和列表面板在密度上对齐

### 8.5 其他后台页

包括但不限于：

- `CategoryManagementPage`
- `ReportPage`
- `AdminKaoyanDataPage`
- `KaogongDataPage`
- `AdminMaterialReviewPage`
- `AdminQuestionBankPage`
- `AdminQuestionsPage`

统一要求：

- 优先迁移到后台共享容器和操作语义
- 尽量减少继续使用前台 `feature-card` / `track-card` 作为后台主结构
- 新增后台样式必须基于 token 与后台语义类，不直接写死局部颜色

## 9. 全局主题切换接入要求

这是本次设计的硬约束。

### 9.1 单一主题来源

后台主题只能跟随现有全局偏好系统：

- `PreferencesPanel`
- `PreferencesContext`
- `document.documentElement.dataset.theme`
- `index.css` 与 `App.css` 中的语义 token

不允许：

- 新增后台独立主题状态
- 在后台页面内直接判断浅色/深色并分支渲染结构
- 通过局部类名绕开全局主题变量

### 9.2 后台新增样式必须 token 化

若后台整理需要新增样式变量，必须在：

- `:root`
- `:root[data-theme='dark']`

中成对定义，并且命名保持语义化。

允许新增的方向：

- 后台面板背景
- 后台筛选器选中态
- 后台摘要卡强调边界
- 后台表格高亮态

不允许：

- 在组件样式中直接硬编码只适合某一主题的背景色
- 在后台局部继续引入 `#fff`、`#0f766e`、`rgba(...)` 作为主题主逻辑

### 9.3 主题切换后的行为预期

切换浅色/深色主题后，后台应满足：

- 容器层级仍然清楚
- 状态 chip 仍然可读
- 筛选器选中态仍然清晰
- 表格 hover / selected / active 态仍然稳定
- 表单输入、消息面板、操作按钮不会出现“浅色方案可读、深色方案发灰”或反向问题

## 10. 测试与验证策略

### 10.1 静态测试

扩展 `frontend/src/App.adminTheme.test.js`，至少覆盖：

- 后台共享样式继续只使用语义 token
- 关键后台页面不再依赖旧的前台标签方案作为主筛选器
- 后台页面继续复用共享后台语义类

建议增加的断言方向：

- 后台筛选器类存在且使用 token
- `ReviewPage` 与 `UserManagementPage` 不再把 `tag tag-btn` 作为主交互筛选实现
- 后台新增样式段不出现浅色硬编码

### 10.2 视觉验证

至少验证以下页面：

- `/admin`
- `/admin/review`
- `/admin/users`
- `/admin/employment`

每页至少验证：

- 浅色主题
- 深色主题
- 打开全局偏好面板后再切换主题

### 10.3 验收重点

验收时重点观察：

- 后台是否看起来属于同一套系统
- 后台与前台是否仍保持同一品牌主题
- 全局主题切换后后台是否完整响应
- 摘要区、工具区、数据区是否形成稳定层级
- 操作按钮与状态表达是否更利于扫读和决策

## 11. 风险与取舍

风险：

- 后台页当前存在不少历史类名混用，迁移时如果只改外观不改结构，会留下新的不一致。
- `App.css` 体量较大，后台整理时需要避免继续堆叠例外规则。
- 个别后台页可能同时承担“表单维护 + 列表管理 + 状态动作”三种职责，整理时要控制范围，避免演变成布局重写。

取舍：

- 本轮优先统一后台语义、层级和主题映射。
- 不追求一次把所有管理页做成完全相同的视觉模板。
- 只要后台页能共享同一种层级逻辑与主题语言，就允许在不同业务页保留少量结构差异。

## 12. 成功标准

- 后台页不再明显带有前台内容卡片拼接感。
- 后台首页、审核页、用户页、就业管理页在层级与语义上看起来属于同一套控制台。
- 后台新增或重构样式全部接入全局主题 token。
- 浅色/深色主题切换后，后台在可读性、层级、状态表达上都保持稳定。
- 后续新增后台页可以继续沿用这套后台语义样式，而不是重新拼装前台类名。
