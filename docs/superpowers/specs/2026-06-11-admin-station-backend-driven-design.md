# frontendv1 管理员主站后端驱动重设计

日期：2026-06-11

主题：基于当前后端真实管理员能力，重新定义 `frontendv1` 的管理员子系统，使其从“通用后台首页”转为“值班总台 + 专项工作台 + 深层处理页”的治理型前端。

## 1. 目标

本设计只解决管理员站，不覆盖游客站与学生方向站的完整实现。

本设计的目标是：

- 按后端真实功能组织管理员前端，不沿用旧 `frontend` 的通用后台结构。
- 让管理员首页承担“分诊与值班”职责，而不是展示型仪表盘职责。
- 让不同性质的后端功能进入不同类型的工作台，而不是共用一套模板页。
- 保证所有管理员功能都能逐层深入，并且返回路径清晰。
- 在风格上做成商业化治理中台，而不是学生站变体或通用管理模板。

## 2. 后端事实依据

当前管理员相关能力来自以下控制器：

- `backend/src/main/java/com/graduateplatform/admin/controller/AdminController.java`
- `backend/src/main/java/com/graduateplatform/admin/controller/AdminQuestionBankController.java`
- `backend/src/main/java/com/graduateplatform/admin/controller/AdminQuestionController.java`
- `backend/src/main/java/com/graduateplatform/job/controller/AdminEmploymentController.java`
- `backend/src/main/java/com/graduateplatform/kaoyan/controller/AdminKaoyanController.java`
- `backend/src/main/java/com/graduateplatform/kaoyan/controller/AdminMaterialController.java`

从这些接口可以确认的管理员一级能力如下：

### 2.1 社区治理

- 帖子待审
- 帖子审核记录
- 帖子举报处理
- 评论举报处理
- 帖子分类管理
- 用户状态管理

### 2.2 题库治理

- 题库分页、创建、更新、删除、启停

- 题目批量创建

### 2.3 考研治理

### 2.4 考公治理

- 简历概览
- 通知触发

## 3. 设计判断

### 3.1 管理员不是“看板用户”，而是“处理用户”

虽然当前后端存在 `/api/admin/dashboard`，但其能力只提供总量摘要，不足以支撑完整大屏式首页。相反，绝大多数管理员接口都在围绕以下动作展开：

- 审核
- 举报处理
- 状态切换
- 数据维护
- 批量导入
- 运营触发

因此管理员首页不应继续设计为“大盘 + 模块卡片墙”，而应设计为值班总台。

### 3.2 首页负责分诊，工作台负责处理

管理员站必须显式分成三层：

1. 值班总台
2. 专项工作台
3. 具体处理页

这样可以避免把所有管理能力摊在一个页面上，也能自然建立稳定返回路径。

### 3.3 同类统一，不同类分化

管理员二级页不采用“全部统一”或“全部完全不同”，而采用以下原则：

- 同类功能共享工作台骨架
- 不同类功能使用不同页面结构与控件组合

这是兼顾辨识度、可维护性和后端功能适配度的最佳平衡点。

## 4. 信息架构

### 4.1 第一层：管理员值班总台

管理员进入站点后直接到达值班总台。

值班总台只承担三类内容：

- 真实待办
- 业务入口
- 最近处理与快捷返回

首页不展示大面积介绍文案，不展示营销式欢迎区，不展示无处理价值的概览卡片墙。

#### 首页待办带

固定展示四个高优先级待办入口：

- 帖子待审
- 举报处理
- 资料待审
- 异常用户

#### 首页业务入口

固定展示五个一级工作入口：

- 社区治理
- 题库治理
- 考研治理
- 考公治理
- 就业运营

#### 首页辅助区

展示两类信息：

- 最近处理记录
- 快速回到上次工作位置

### 4.2 第二层：三类工作台

#### 审核流工作台

适用模块：

- 社区治理
- 考研资料审核

核心结构：

- 顶部筛选带
- 左侧待办队列
- 中部详情区
- 底部或右下动作区

适配原因：

- 后端能力以待审、举报、审核结果、处理原因为核心
- 主要动作是“阅读 -> 判断 -> 决策”

#### 数据治理台

适用模块：

- 题库治理
- 考研院校与分数线治理
- 考公岗位、分数线、日历治理

核心结构：

- 顶部检索与批量操作区
- 中部数据主表
- 右侧对象摘要与关联信息区

适配原因：

- 后端能力以分页、筛选、增删改、启停、导入、快照为核心
- 主要动作是“查找 -> 编辑 -> 批量治理”

#### 运营台

适用模块：

- 就业运营

核心结构：

- 顶部节奏带
- 中部运营画布
- 右侧结果与触达摘要

适配原因：

- 后端不只是简单数据维护，还包括通知触发、招聘会与岗位联动、简历概览
- 主要动作是“调度 -> 触发 -> 看结果”

### 4.3 第三层：具体处理页

第三层不再按模块统一，而是按动作类型拆页。

#### 审核型页面

- 帖子审核详情
- 举报处理详情
- 评论举报处理详情
- 资料审核详情

结构原则：

- 一次只处理一个对象
- 原文和处理原因并列可见
- 动作反馈必须明显

#### 治理型页面

- 题库详情
- 题目列表
- 题目编辑
- 题目批量导入
- 题目快照
- 院校编辑
- 分数线编辑
- 考公岗位编辑
- 日历事件编辑

结构原则：

- 列表页只负责浏览与筛选
- 编辑、导入、快照进入独立深页或抽屉
- 不在一个页面同时承担过多动作

#### 运营型页面

- 招聘会管理
- 招聘会详情或编辑
- 岗位管理
- 简历概览
- 通知触发页

结构原则：

- 节奏信息优先
- 动作结果可见
- 不做单纯的“表格管理页”

## 5. 模块落位

### 5.1 社区治理

挂在审核流工作台下，包含：

- 帖子待审
- 审核记录
- 帖子举报
- 评论举报
- 分类管理
- 用户状态管理

其中：

- 帖子待审、帖子举报、评论举报使用审核流骨架
- 分类管理、用户状态管理仍从社区治理进入，但可在同一工作台下切换到治理式子页

### 5.2 题库治理

挂在数据治理台下，包含：

- 题库列表
- 题库详情
- 题目列表
- 题目编辑
- 批量新增
- 文件导入
- 题目快照

### 5.3 考研治理

挂在数据治理台下，包含：

- 院校数据
- 分数线数据
- 资料审核入口
- 资料全量管理

其中：

- 院校和分数线保持数据治理结构
- 资料审核从考研治理进入，但实际处理页切换到审核流骨架

### 5.4 考公治理

挂在数据治理台下，包含：

- 岗位数据
- 分数线数据
- 日历事件

### 5.5 就业运营

挂在运营台下，包含：

- 招聘会管理
- 岗位管理
- 简历概览
- 通知触发

## 6. 控件选型规则

这部分是本设计与旧 `frontend` 最大的区别：同样是“一个功能入口”，不同后端能力必须对应不同控件。

### 6.1 队列型控件

用于：

- 帖子待审
- 帖子举报
- 评论举报
- 资料待审

选型：

- 左侧窄队列
- 中部原文详情
- 固定动作区

不选普通数据表的原因：

- 审核不是看数据矩阵，而是处理具体对象

### 6.2 治理表格型控件

用于：

- 题库
- 题目
- 院校
- 分数线
- 考公岗位
- 日历事件

选型：

- 顶部过滤板
- 主数据表
- 批量工具条
- 右侧对象摘要

不选卡片瀑布或门户式列表的原因：

- 后端提供的是治理接口，不是内容消费接口

### 6.3 步骤面板与抽屉

用于：

- 文件导入
- 批量新增
- 通知触发
- 快照浏览

选型：

- 抽屉
- 步骤面板
- 时间轴

不把这些动作留在主列表页内弹几个小框解决。

### 6.4 风险状态面板

用于：

- 用户状态管理

选型：

- 状态标签
- 风险摘要
- 明确的状态切换动作
- 原因输入区

不做成普通用户表格页，因为用户状态处理本质上带治理决策属性。

## 7. 返回路径规则

所有管理员深页都必须有显式返回路径，不能依赖浏览器后退。

统一返回规则为：

`值班总台 -> 业务工作台 -> 列表页 -> 详情/编辑/审核 -> 原列表 -> 业务工作台 -> 值班总台`

### 7.1 社区审核路径

`值班总台 -> 社区治理 -> 帖子待审 -> 审核详情 -> 帖子待审 -> 社区治理 -> 值班总台`

### 7.2 题库治理路径

`值班总台 -> 题库治理 -> 题库详情 -> 题目列表 -> 题目编辑/批量导入/快照 -> 题目列表 -> 题库详情 -> 题库治理 -> 值班总台`

### 7.3 考研资料审核路径

`值班总台 -> 考研治理 -> 资料待审 -> 审核详情 -> 资料待审 -> 考研治理 -> 值班总台`

### 7.4 就业运营路径

`值班总台 -> 就业运营 -> 招聘会管理/岗位管理 -> 详情或编辑 -> 列表 -> 就业运营 -> 值班总台`

## 8. 交互提示原则

用户此前明确要求提示不能不明显，因此管理员站的状态反馈遵循以下规则：

- 审核通过、驳回、下线、删除、导入完成、通知触发完成都必须给出明显反馈
- 反馈文案使用动作结果，不用模糊提示
- 高风险动作必须在动作前给出确认语义
- 空状态页面必须告诉管理员下一步去哪里，而不是只显示“暂无数据”

示例：

- “已通过该帖子，返回下一条待审内容”
- “资料已驳回，请继续处理队列”
- “已触发 126 条站内通知，2 条因重复发送被跳过”

## 9. 视觉方向

管理员站采用“商业化治理中台”方向，不复用学生站的内容门户语言。

视觉目标：

- 克制
- 密度高但不拥挤
- 强层级
- 强秩序
- 少装饰

关键特征：

- 首页像值班台，不像欢迎页
- 审核页像工单处理台
- 数据治理页像编辑中台
- 运营页像调度盘

避免：

- 大块模板卡片堆叠
- 统一 hero 区
- 为了“现代感”而大量使用通用渐变和圆角卡片
- 用一套壳套全部管理员页面

## 10. 不在本设计内的内容

本设计不处理以下事项：

- 游客站与学生方向站的完整信息架构
- 与真实后端联调后的接口兼容细节
- 视觉像素级样式稿
- 最终前端路由与组件拆分方案

这些内容应在后续实现规划中继续展开。

## 11. 实施成功标准

当管理员站完成初版实现后，应满足以下判断标准：

- 首页不再像通用后台首页
- 用户进入任一模块时，能明显感知当前是在“审核”、“治理”还是“运营”
- 任一深页都能顺着显式路径返回，不出现迷路
- 同一管理员站内不同模块的页面结构有真实差异，不是换标题和颜色
- 页面组织方式能够让有数据状态和无数据状态都清晰可读
