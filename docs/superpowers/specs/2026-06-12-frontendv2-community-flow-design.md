# frontendv2 社区主流程重构设计

## 目标

本次设计只聚焦 `frontendv2` 的社区主流程重构，不追求把旧版 `frontend` 的页面结构原样搬过来，而是保留 `frontendv2` 更清晰的路线，同时吸收旧版里真正顺手的使用体验。

这次重构的核心目标有四个：

1. 让社区主流程稳定收束为“目录页 -> 发帖页 -> 详情页 -> 通知页”的清晰路线。
2. 优先补齐影响主流程连续性的功能接入，尤其是发帖、评论、附件、点赞收藏和通知跳转。
3. 修正当前 `frontendv2` 中“路线清楚但手感偏硬”的问题，让常用操作更直接、反馈更明确。
4. 保持 `frontendv2` 为主前端，不把这次社区重构扩散成 `frontend`、认证层或全站布局的大迁移。

## 范围

### 本次在范围内

- `frontendv2` 社区目录页、发帖页、帖子详情页、通知页
- 社区相关展示逻辑、交互反馈、筛选状态、评论树和附件交互
- 对现有 `communityApi` 的必要补充和前端调用整理
- 社区页面的测试补充与回归验收

### 本次不在范围内

- 重写 `frontend` 旧版社区页面
- 改造全站认证体系或 `@legacy/context/AuthContext.jsx`
- 改造 `frontendv2` 之外的方向站点、管理端或全局布局壳
- 对后端接口进行大规模重构

## 产品方向

本次方案采用“`A 为主，吸收一点 B`”的方向：

- 保留 `frontendv2` 的独立发帖页，不把完整发帖体验塞回目录页。
- 吸收旧版 `frontend` 的优点，但不机械对齐视觉和交互细节。
- 目录页承担“发现与进入”，发帖页承担“生产内容”，详情页承担“阅读与互动”，通知页承担“提醒与回流”。

这意味着最终体验不是“尽量像旧版”，而是“保留旧版低思考成本的操作手感，同时让页面职责更稳定”。

## 信息架构

## 1. 社区目录页 `/community`

### 职责

- 展示帖子列表
- 提供搜索、分类、排序、标签、附件筛选
- 展示精选或最近讨论等辅助信息
- 提供清晰的发帖入口
- 负责进入帖子详情页

### 不承担的职责

- 完整发帖编辑
- 复杂评论互动
- 举报原因填写

### 设计要求

- 首屏就能开始使用，不需要先理解全部页面结构
- 搜索和筛选都保持可见，不要把高频入口藏得过深
- 返回目录页时尽量保留关键词、分类、标签、附件筛选和页码上下文
- 空结果、加载失败、演示模式都必须告诉用户下一步能做什么

## 2. 发帖页 `/community/new`

### 职责

- 填写标题、分类、可见范围、匿名设置
- 编辑正文和标签
- 填写附件说明与上传附件
- 提交审核或保存草稿

### 不承担的职责

- 浏览社区列表
- 承载评论互动
- 处理社区通知

### 设计要求

- 表单按“基础信息 -> 正文 -> 附件 -> 提交”分区，而不是一整页松散字段
- 用户在提交前能看到简短摘要，知道当前已填写了哪些关键项
- 游客、演示身份、真实登录用户的可操作性差异要尽早提示
- 提交完成后必须给出明确去向，优先进入新帖详情页，其次回到目录页

## 3. 帖子详情页 `/community/:postId`

### 职责

- 阅读正文
- 查看附件说明与下载附件
- 点赞、收藏、举报帖子
- 评论、回复、编辑、删除、举报评论

### 不承担的职责

- 社区全局筛选
- 新帖创建

### 设计要求

- 正文、附件、评论、互动动作应保持在同一阅读流附近
- 评论交互必须让用户明确知道自己正在回复谁、编辑哪条内容
- 点赞、收藏、评论提交、删除等动作完成后要立即有明确反馈
- 详情页返回目录页时，优先恢复原有浏览上下文

## 4. 通知页 `/community/notifications`

### 职责

- 展示社区互动提醒
- 区分未读和全部通知
- 将用户引导回对应帖子继续处理

### 不承担的职责

- 替代帖子详情页完成评论或举报动作
- 承担社区目录的筛选职责

### 设计要求

- 通知页只负责“提醒与回流”，不和目录、发帖页混放职责
- 用户从通知返回原帖后，应能继续处理评论、举报或附件操作
- 已读标记和未读筛选要可见且可验证

## 用户流程

### 浏览与互动主流程

1. 用户进入目录页浏览帖子列表。
2. 用户通过分类、排序、标签、关键词或附件筛选缩小范围。
3. 用户进入帖子详情页阅读正文、查看附件说明、下载附件或参与评论互动。
4. 用户返回目录页时保留浏览上下文，继续浏览下一篇内容。

### 发帖主流程

1. 用户从目录页进入发帖页。
2. 用户依次完成基础信息、正文、附件说明和上传。
3. 用户选择“提交审核”或“保存草稿”。
4. 提交成功后进入帖子详情页或返回目录页，并得到明确成功反馈。

### 通知回流流程

1. 登录用户进入通知页查看提醒。
2. 用户筛选未读通知或标记通知已读。
3. 用户点击通知回到对应帖子详情页继续处理具体互动。

## 吸收旧版的体验点

本次只吸收 `frontend` 旧版中确实改善使用效率的部分。

### 目录页要吸收的点

- 搜索、分类、排序、标签、附件筛选在首屏范围内可见
- 发帖入口始终明确，不需要滚动很深才能找到
- 帖子卡片提供足够判断信息，包括分类、标签、摘要、附件状态和互动量
- 返回目录后保留原有筛选和浏览状态
- 空结果要给用户具体建议，而不是只提示“暂无内容”

### 发帖页要吸收的点

- 分区清晰，降低首次发帖的认知压力
- 提交按钮文案明确区分“保存草稿”和“提交审核”
- 尽早告知当前身份是否真的能提交
- 在提交前提供简短摘要，减少“填了很多但不知道现在缺什么”的感觉

### 详情页要吸收的点

- 阅读与互动集中，不要让用户来回寻找入口
- 评论回复和编辑有明确目标感
- 点赞、收藏、举报和附件下载都应有即时结果反馈
- 附件说明与下载动作邻近展示，避免用户下载后才知道怎么使用

### 明确不照搬的点

- 不把完整发帖重新塞回目录页弹层作为主流程
- 不让目录页同时承担浏览、发帖、评论、举报等过多职责
- 不继续依赖 `prompt`、`confirm` 一类原始交互完成核心流程

## 功能优先级

## 第一优先级：主流程必须走通

### 目录页

- 列表加载稳定
- 分类、排序、关键词、标签、附件筛选都可组合使用
- 翻页可用
- 返回目录时尽量保留筛选状态

### 发帖页

- 分类加载正确
- 标题、正文、标签、可见范围、匿名、附件都能正常提交
- 支持提交审核与保存草稿
- 提交成功后跳转路径正确

### 详情页

- 正文展示正常
- 评论列表可见
- 发布评论、回复评论、编辑评论、删除评论可用
- 点赞、收藏和附件下载可用

## 第二优先级：让流程不别扭

- 举报帖子与举报评论流程完善
- 加载中、提交中、空态、权限不足、未登录和演示模式提示明确
- 目录、发帖、详情之间的返回路径更自然

## 第三优先级：增强但不阻塞主线

- 目录页快速开始区或更明显的发帖入口
- 草稿提示、最近讨论、热门标签等增强模块
- 评论目标高亮、局部刷新和更细的成功反馈

## 代码结构设计

本次重构以页面内部收束为主，只做必要的轻量拆分。

## 1. 主要修改文件

- `frontendv2/src/pages/community/CommunityHubPage.jsx`
- `frontendv2/src/pages/community/CommunityComposerPage.jsx`
- `frontendv2/src/pages/community/CommunityPostPage.jsx`
- `frontendv2/src/pages/community/CommunityNotificationsPage.jsx`
- `frontendv2/src/lib/communityUi.js`
- `frontend/src/lib/api.js`（仅在社区 API 存在必要缺口时小范围补充）

## 2. 建议新增组件

- `frontendv2/src/components/community/CommunityFilterPanel.jsx`
- `frontendv2/src/components/community/CommunityPostCard.jsx`
- `frontendv2/src/components/community/CommunityCommentThread.jsx`
- `frontendv2/src/components/community/CommunityCommentComposer.jsx`
- `frontendv2/src/components/community/CommunityPostActions.jsx`

### 拆分原则

- `pages/community` 继续作为路由页面入口
- 页面文件负责页面状态、数据拉取与跳转
- 组件文件负责展示与局部交互块
- `communityUi.js` 只保留纯格式化、纯 normalize 和无状态树操作

## 3. 明确暂不处理的代码区域

- `frontend/src/pages/CommunityPage.jsx`
- `frontend/src/pages/CommunityDetailPage.jsx`
- `frontendv2/src/App.jsx` 的整体路由结构
- `frontendv2/src/layouts/*`
- `@legacy/context/AuthContext.jsx`

本次只把这些位置作为参考或依赖，不作为主改造目标。

## 数据与状态策略

### 目录页状态

- 继续使用 URL query 保存筛选和分页状态
- 目录页是浏览上下文的唯一来源
- 详情返回目录时优先恢复 query 状态，而不是重置成默认页

### 发帖页状态

- 使用页面本地状态管理表单
- 所有可提交字段在提交前统一校验
- 演示身份与未登录用户在进入提交动作前就得到限制提示

### 详情页状态

- 帖子、评论、附件下载状态、评论编辑状态、举报状态分开管理
- 评论树更新应通过纯函数工具完成，避免散落更新逻辑
- 帖子互动计数更新应尽量局部完成，减少无意义整页重拉

### 通知页状态

- 通知列表与筛选状态只服务通知页自身
- 标记已读后直接更新本地状态，并在真实接口模式下同步服务端

## 错误处理与反馈要求

### 统一要求

- 所有关键动作都要有可见反馈，包括加载、成功、失败和权限不足
- 错误提示要说明下一步，而不是只显示“失败”
- 演示模式和真实接口模式的差异必须明确显示

### 关键场景

- 列表加载失败时提示重新筛选或稍后重试
- 发帖失败时保留用户输入，不清空表单
- 评论提交失败时保留内容并提示原因
- 附件下载失败时提示重试
- 未登录触发互动时直接提示需要登录

## 测试与验收标准

## 1. 主流程验收

### 目录页

- 帖子列表能正常加载
- 搜索、分类、排序、标签和附件筛选可用
- 翻页可用
- 返回详情后能尽量保留原有筛选上下文
- 发帖入口清晰可见

### 发帖页

- 分类可加载
- 标题、正文、标签、匿名、可见范围、附件都能填写
- 保存草稿和提交审核文案及行为清楚
- 游客与演示身份提示正确
- 提交成功后的跳转路径符合预期

### 详情页

- 正文正常展示
- 附件说明与下载可用
- 点赞、收藏、举报可用
- 评论、回复、编辑、删除可用
- 当前回复或编辑目标清晰

### 通知页

- 登录用户可查看通知
- 未读与全部筛选可用
- 标记已读后状态更新
- 能跳转回对应帖子继续处理

## 2. 体验验收

达到以下标准才算重构成功：

- 用户一进入社区就知道下一步能做什么
- 用户从目录进入详情再返回时不迷路
- 用户想发帖时不会被额外结构阻挡
- 用户互动后能立刻看到明确反馈
- 空态、报错、未登录和演示模式都不让用户困惑

## 3. 技术验收

- `frontendv2` 下 `npm run build` 通过
- `frontendv2` 下 `npm test` 通过
- 社区相关测试至少覆盖：
  - 路由可达
  - 目录页基础渲染与筛选
  - 发帖页基础提交流程
  - 详情页评论与互动关键行为
  - 登录态与游客态差异

## 实施顺序

建议按以下顺序实施：

1. 先整理目录页状态、入口和筛选体验。
2. 再补发帖页的完整闭环。
3. 再打磨详情页的评论、附件和互动行为。
4. 最后整理通知页与相关回流路径。
5. 在过程中逐步抽取 `components/community/*` 公共组件。

这个顺序优先保证主流程不断，再逐步打磨手感与复用结构。

## 当前决策结论

以下决策已经确认：

- 社区重构主线只做 `frontendv2`
- 优先目标是“梳顺路线”，然后“补功能接入”，最后“补交互反馈”
- 不要求尽量对齐旧版，而是只借鉴旧版真正顺手的部分
- 页面职责固定为目录页、发帖页、详情页、通知页四段
- 保留独立发帖页，不把完整发帖回塞到目录页
- 代码层只做轻量拆分，不扩散成全站架构重构
